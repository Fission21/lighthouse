# 0006 - 一窗一进程、单域名路径分流与无状态 HTTP

- **状态**：已采纳
- **日期**：2026-09-24（记录既有决策；一窗一进程与路径分流自 0.5.0 起，无状态传输自 0.6.0 起）
- **决策人**：项目所有者 + AI
- **标签**：#architecture
- **关键词**：`一窗一进程`, `单域名`, `路径分流`, `stateless_http`, `registry`, `render_ingress`

## 一、背景

一个窗口 = 一个目录 + 一套范围。窗口会变多（demo / 项目 / 资料库），接入方式也各不相同（隧道、局域网、公网 IP 直连）。进程模型、域名模型和会话模型都需要定下来。

## 二、考虑的方案

| 方案 | 优点 | 代价 |
|---|---|---|
| 单进程多窗口 | 省资源 | 一个窗口崩全崩；范围隔离靠代码自律 |
| 一窗一进程 | 故障与范围天然隔离，可单独重启 | 窗口数增长 = 进程数增长 |
| 每窗口一个域名 | 配置直观 | 加窗口要动 DNS 与证书 |
| 单域名 + 路径分流 | 加窗口不动 DNS | 路径规则顺序敏感 |
| 有状态会话 | 协议默认行为 | 服务一重启，客户端会话作废 |

## 三、决策

- **一窗一进程**：一个窗口崩了不影响别的；范围完全隔离；可单独重启。
- **范围写 JSON 不写代码**（`windows.json`）：改范围不用改代码、不用重新审代码；服务每次调用现读注册表与开关，改了立刻生效。
- **单域名 + 路径分流**（`core/render_ingress.py`）：加窗口不再动 DNS，也不用给每个窗口一条证书/记录。
- **无状态 HTTP**（`stateless_http`）：工具全是请求-应答式，不需要会话状态。有状态时服务一重启，客户端手里的会话就作废，而不少客户端不自动重连、继续拿旧会话 id 调用 → 服务端回 "Session not found" → 对方误以为"找不到 mcp 环境"。无状态后重启对已连客户端完全无感。

## 四、后果与风险

- 正面：故障隔离、范围隔离、重启无感、加窗口零 DNS 操作。
- 代价：进程数随窗口增长；路径规则**顺序敏感**（具体路径在前，404 兜底在后），手改隧道配置会被下一次 render 覆盖。
- 持续跟踪：新增窗口时确认 ingress 重新渲染且顺序正确；无状态传输下不要引入依赖服务端会话的功能。
